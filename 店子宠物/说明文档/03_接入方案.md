# 接入方案：把「促销利润防护」并入 ai-marketing-ops

> 目标：队友的 MVP 不动骨架，我这边以「新增模块 + 新增一个入口 + 一条交叉提示」的方式并入，
> 形成"内容 skill + 利润 skill 共用一套商品数据"的完整作品。

---

## 一、队友成品体检结论

**技术栈**：FastAPI + SQLAlchemy(SQLite) + 原生 JS 单页（无构建步骤）+ OpenAI 兼容 LLM（DeepSeek，Mock 兜底）。
**跑法**：`一键启动.bat` 自建 venv、装依赖、起 uvicorn 8000，浏览器打开即用。

**已有能力（4 个）**

| 能力 | 实现位置 | 说明 |
|---|---|---|
| 商品结构化提取 | services/extraction.py | 粘贴原始资料 → 结构化字段，缺字段进 missing_fields 而不是编 |
| 平台化内容生成 | services/content.py + config/platforms.yaml | 小红书/抖音/详情页三套策略，含 script 分镜 |
| 内容合规审核 | services/audit.py | 事实/合规/格式校验 |
| 热点发现与匹配 | services/hotspots.py + services/matching.py | 两阶段匹配 + `S=0.30R+0.25T+0.20A+0.15P+0.10C` 评分 |

**三个做得好的地方（评审会认可）**
1. **规则外置**：平台策略在 `platforms.yaml`，改规则不改代码。
2. **AI 不猜参数**：`llm.complete_json` 用 Pydantic Schema 约束输出；缺数据标"待确认"。
3. **Mock 兜底**：没有 API Key 也能跑完整流程，演示不依赖网络。

**三个缺口（正好是我要补的）**
1. **没有对话式 Agent**。全站是"表单 + 按钮"，没有一处可以自然语言对话——而官方 25 分的「Agent 应用成果」里，15 分直接看提示词示例对话输出。这是最大的结构性缺口。
2. **README 写了"成本与风险审核"，实际只审合规**。`audit.py` 不碰价格与利润，"毛利为负时提示停止"只写在 README 第 93 行，代码里没有。
3. **热点是演示数据**（`DEMO_HOTSPOTS` + 哈希正弦波模拟热度），对外表述必须写"接口预留，接入需授权"，否则有失实风险。

## 二、一句话说清接入方式

> 引擎放**服务层**（services/pricing.py），对话放**路由层**（routers/agent.py），
> 界面加**第 4 个入口**（利润防护），内容页加**一条利润提示**。
> 他的现有代码一行不用改，只在 `main.py` 注册一行路由、`seed.py` 加三个真实 SKU。

## 三、改动清单（文件级）

### 新增

| 文件 | 作用 | 关键点 |
|---|---|---|
| `app/services/pricing.py` | 测算引擎（纯函数） | 入参用 Pydantic；输出"拆解"而非单一利润；无副作用、可单测 |
| `app/services/agent.py` | 对话编排 | 抽取参数 → 缺口追问 → 调引擎 → 归因解释 → 越权拦截 |
| `app/routers/agent.py` | 对话接口 | `POST /agent/chat`、`GET /agent/session/{id}` |
| `config/pricing_policy.yaml` | 利润红线与默认口径 | 与 `platforms.yaml` 同风格，改规则不改代码 |
| `frontend` 内第 4 个 panel | 对话 + 账单卡 | 复用现有 CSS，`data-panel="profit"` |
| `tests/test_pricing.py` | 引擎单测 | 用标准库 `unittest`，不新增依赖 |

### 修改（只碰两处，且都是加法）

| 文件 | 改动 |
|---|---|
| `app/main.py` | 增加 `app.include_router(agent.router)` 一行 |
| `app/seed.py` | 增加 3 个真实 SKU（SR-72 / J20 涵道 / 赛斯纳），带真实成本 |

### 新增数据表（不改现有表结构）

- `PromoConfig`：店铺促销配置（券面额、满件折扣、生效期、平台）
- `ProfitCheck`：每次测算记录（入参快照 + 结果拆解 + 归因文本）
- `AgentSession`：对话上下文（多轮参数逐步补齐）

> 只加表不改表，队友的 `Product` / `Content` / `Match` 全部保持原样，合并零风险。

## 四、接口设计

```
POST /agent/chat
  body: { "session_id": "uuid", "message": "我打算上两件八折，再发 29 元券，卖 SR-72 会亏吗？" }
  resp: {
    "action": "clarify | bill | refuse",
    "reply": "……",                      // 给人看的话
    "clarify_fields": ["成本口径", "佣金基数"],   // action=clarify 时
    "bill": { "成交额": 447.80, "商品成本": 476.00, "平台佣金": 28.06,
              "利润": -56.26, "利润率": -12.6 },  // action=bill 时
    "options": [{"name": "撤券", "profit": -29.00}, ...]
  }

GET /products/{id}/profit?promo=…     # 供内容页调用，返回一行结论
```

`action` 只有三个取值，这是硬约束：**先问清 → 再算 → 该拒就拒**，不存在"边猜边算"。

## 五、对话怎么落到代码（四步，每步都有刹车）

1. **抽取**：LLM 只做一件事——把话变成 JSON `{意图, SKU, 数量, 促销项[], 缺失项[]}`。不产生任何数字。
2. **刹车一：缺口追问**。`缺失项` 非空就只追问，**不调引擎**。对应脚本第 1 轮。
3. **计算**：参数齐了才调 `pricing.run()`，拿到账单拆解。
4. **解释**：把账单作为 `facts envelope` 注入 prompt，模板里写死"只能引用以下字段里的数字"。LLM 负责措辞，不负责算术。
5. **刹车二：越权拦截**。意图命中"改价/发券/改活动/改库存"→固定拒绝话术，附"请你在后台自行确认"。

> 这两道刹车就是答辩时的护身符：评委问"AI 会不会算错"，答案是"它没有算的机会"。

## 六、怎么证明两个技能共用一套底座（PPT 用这一条）

演示动线：

```
内容页 → 选 SR-72 → 生成小红书文案
      → 页面顶部出现红条："当前促销配置下利润 −56.26（−12.6%），建议先调整折扣"
      → 点「去测算」→ 跳到利润防护页，上下文已带入
```

一句话解释：**同一条商品数据，两个视角，一个账本。** 如果两边各算一套，这里就会自相矛盾。
