## 1. 能力一：平台宣传 Skill + 生成前产品分析 + 事实校验（防幻觉内容引擎）

### 1.1 成果
内容生成从「一个通用提示词」升级为**五段流水线**，专治「AI 幻觉 / 文案和产品无关」：

```
①生成前产品分析(规则化,零LLM) → ②加载平台Skill(md注入) → ③大模型生成(只许用事实清单)
  → ④事实校验(程序化,防幻觉) → ⑤合规校验(禁用词/长度/标签数) → 高问题自动重写一次
```

### 1.2 核心设计（框架无关）

**分层三文件**（这是移植的核心思想）：
- **机器可读硬性限制** → 放 YAML/JSON（标题长度、标签数、禁用词、结构骨架）；
- **写给模型的写作规范** → 放 Markdown（标题公式、钩子、红线），生成时整段注入提示词；
- **装配代码** → 只负责「读文件 + 拼提示词」，改规范不碰代码。

### 1.3 数据结构与配置 schema

`platforms.yaml` 每个平台一张配置（可整体替换为 JSON / 数据库表）：

```yaml
xiaohongshu:
  name: 小红书
  type: 种草型
  strategy: 生活场景、使用体验、细节展示、真实感
  algorithm: 双列瀑布流；首图+标题决定点击率，点击后互动（收藏>评论>点赞）决定第二波推荐…
  core_metrics: [点击率, 收藏率, 评论率, 搜索长尾]
  skill: platform_skill_xiaohongshu.md      # 指向对应的 md
  title_max_length: 20
  tags_max: 10
  cta_style: 自然引导关注与收藏，避免硬广
  tone: 真实、亲切、第一人称体验
  emoji: true
  forbidden_words: [最, 第一, 国家级, 顶级, 绝对, 根治, 治疗, 100%, 全网最低]
  structures: [场景引入, 使用体验, 细节与差异点, 互动引导]
```

`platform_skill_<platform>.md` 固定六节（每节是给模型看的规则）：

```
一、平台怎么给流量（算法/指标）
二、内容结构公式
三、标题公式
四、开头钩子
五、写作红线
六、把商品分析用起来
```

### 1.4 防幻觉三层 + 校验规则

**第 1 层：Skill 注入** — `load_platform_skill(platform)` 按 mtime 缓存读取 md，整段拼进 system 提示词；
硬性限制（yaml）另拼一段，规则冲突时硬性限制优先。

**第 2 层：生成前产品分析 `build_product_brief(product)`** — 纯规则、零 LLM、秒回。只做「提炼与归类」，绝不新增事实。输出：

```
core_points(卖点)  audience{描述,需求,顾虑}  scenes  pain_points
evidence(证据)  restrictions(禁忌)  hot_topic_types(可蹭热点类型)
facts(事实清单,逐条)  numbers(允许出现的数字白名单)  gaps(资料缺口)
angles(4平台切入角度)  doc(拼给模型的完整文本)
```

**第 3 层：生成后事实校验 `fact_check(content, product, brief)`** — 程序化，4 条规则：

| 规则 | 判定 | 级别 |
|---|---|---|
| 数字白名单：文案里每个数字必须来自 `allowed_numbers` | 价格语境不符 | high |
| | 普通数字找不到来源 | warn |
| 成本泄露：文案出现 `cost_price` 的数字 | 命中 | high |
| 无依据宣称：出现「专利/认证/获奖/销量第一/国家级/检测报告/疗效…」且商品证据里没有 | 命中 | high |
| 商品名/品类未命中 | 未命中 | warn |

`passed = 无 high 问题`；有 high 问题则**带问题清单重写一次，取 high 更少的版本**。

> 配套修复 `audit.py`：「最怕」「第一步」「最近」这类日常表达不再被误判为极限词，
> 只有「最+好/佳/大/小/便宜…」和「全国/全网/行业/销量+第一」才拦截。

### 1.5 移植到其他网站的步骤

1. 把 `platforms.yaml` 换成目标站点的配置表（新增平台 = 加一行 + 加一个 skill md，零代码）。
2. 复制 `platform_skill.py` 的 mtime 缓存加载（任何语言等价实现：`stat(mtime) → 缓存字典`）。
3. 把 `build_product_brief` 的字段映射改成目标站点的商品模型字段（只改取值，不改逻辑）。
4. 把 `fact_check` 原样移植（正则 + 集合运算，无依赖）；`_CLAIM_WORDS` 可按行业扩词。
5. 生成接口改返回三元组 `(内容, brief, 校验结果)`，校验结果合进审计备注里回显。

## 2. 能力二：热点采集并发加固 + 状态显性化

### 2.1 成果
「立即采集」从「去重后看起来没反应」变成「新增 X 条 · 更新 Y 条（库中共 N 条）」+ NEW 标记 + 按更新时间排序；并发点击不再重复采集。

### 2.2 核心设计（框架无关）

**① 采集互斥锁**（防双击/定时器并发重复采集）：

```python
_COLLECT_LOCK = threading.Lock()

def collect_hotspots(db):
    if not _COLLECT_LOCK.acquire(blocking=False):
        return {"running": True, "message": "上一次采集还在进行中…"}
    try:
        return _collect_locked(db)   # 真正采集逻辑
    finally:
        _COLLECT_LOCK.release()
```

**② 数据库并发加固**（SQLite 多线程写不锁库）：

```python
# 连接参数
connect_args={"timeout": 30}
# 每次连接后执行
PRAGMA journal_mode=WAL;
PRAGMA busy_timeout=30000;
```

**③ 采集结果显性化**（返回结构化统计，前端据此渲染）：

```json
{"collected": 164, "new": 1, "updated": 163, "total": 265, "demo": false}
```

`_upsert` 按 `(title, source)` 去重，返回 `(新增数, 更新数)`；重复条目只原地更新热度/趋势/更新时间，不新增卡片。

### 2.3 移植步骤

1. 采集入口加一个进程内/分布式锁（单机用 `threading.Lock`，多机换 Redis `SETNX`）。
2. 关系库换成 WAL + `busy_timeout`（Postgres/MySQL 本就有行级锁，跳过这步）。
3. 采集函数返回 `{collected, new, updated, total, running}` 五字段，前端按字段渲染状态条与「本次新增」筛选。

## 3. 能力三：热点看板双分区 + 前端链式调用规范

### 3.1 成果
热点看板从「一个长列表，匹配结果沉底」拆成两个子页：**🔥热点列表 / 🎯AI匹配机会**，任何一方都不会被挤到底部。

### 3.2 核心设计（框架无关）

**① 单一长面板拆成子 Tab**（内容分类、避免沉底）：

```js
let HS_TAB = 'list';
function setHotspotTab(tab) { /* 切换两个容器显示 + 按钮高亮 + 空态占位 */ }
// #hs_tab_list = 采集 + 列表 + 筛选；#hs_tab_match = 匹配按钮 + 结果
```

**② 前端链式调用规范（本次真正的 bug 根因）**：

> 采集成功后要「重新加载列表 → 再标 NEW」。`refreshHotspots` 里写的是
> `return loadHotspots().then(...)`，但 `loadHotspots()` 漏了 `return`，返回 `undefined`，
> 于是 `undefined.then(...)` 抛 TypeError，被 `.catch` 捕获 → 界面误报「采集失败」（后端其实 200 成功）。

规范：**凡是要被 `.then` 链式等待的加载函数，必须 `return` 它的 Promise**：

```js
function loadHotspots() {
  return api('/hotspots').then((items) => {   // ← 必须 return
    HOTSPOTS = items || [];
    renderHotspotFilters();
    renderHotspots();
  });
}
```

### 3.3 移植步骤

1. 内容会「沉底」的长面板，拆成子 Tab + 两个容器，切换只切 `display`。
2. 异步刷新链统一：加载函数一律 `return promise`；统一错误兜底（`.catch` 里区分「网络断连」和「业务失败」两种文案）。

## 4. 通用移植清单（跨能力，可直接照抄）

| 原则 | 落地 |
|---|---|
| 配置外置 | 硬性限制放 YAML/JSON，写作规范放 md，改配置不改代码 |
| 规则校验纯函数化 | `fact_check` / `audit` / 热度归一化都是纯函数，零副作用、易单测 |
| 装配层 mtime 缓存 | 改 md 立即生效、不用重启 |
| 采集/写库加锁 | 单机锁 + WAL + busy_timeout |
| 异步链式规范 | 加载函数 `return` promise；catch 分「断连/业务」两类文案 |
| 结果显性化 | 接口返回 `{total, new, updated, running}`，前端展示增量而非「成功/失败」二字 |

## 5. 移植到「其他网站」的最小落地模板

```
目标站点
├── config/
│   ├── platforms.{yaml,json}            # 硬性限制（按站点换平台）
│   └── platform_skill_<平台>.md          # 写作规范（六节，按站点重写）
├── service/
│   ├── skill_loader                     # mtime 缓存加载 md
│   ├── product_analysis                 # build_product_brief 的等价实现
│   ├── fact_check                       # 数字白名单/成本/宣称/命中 4 规则
│   └── collector                        # 采集 + 锁 + 增量统计
├── db/
│   └── (WAL + busy_timeout / 行级锁)
└── frontend/
    ├── 子 Tab（列表 / AI 结果分区）
    └── 异步链：加载函数 return promise + 分类型错误提示
```

**三步口诀**：① 平台规则落配置与 md；② 内容生成必走「产品分析 → 事实校验 → 重写」三关；③ 采集与列表要「锁得住、看得见增量、分得开区域」。
